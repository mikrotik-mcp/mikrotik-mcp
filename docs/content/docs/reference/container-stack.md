## get_container_logs

**Read Container Logs** · Risk: **read**

Reads what containers wrote to the RouterOS log. A container's output reaches the log only when it was created or updated with `logging=yes`; the lines carry the `container` topic. Use it to see why a container stops, restarts or fails to start. `contains` keeps only the lines with that text (for example an error word or a process name), and `lines` limits the answer to the newest lines. RouterOS does not tag a line with the container's name, so with several logging containers the lines are mixed; filter with `contains`. Returns the newest matching lines, or says that there are none and why that may be.

| Parameter  | Required | Definition                                                        |
| ---------- | -------- | ----------------------------------------------------------------- |
| `contains` | No       | Keep only lines with this text `{"type":"string","maxLength":80}` |
| `lines`    | Yes      | `{"default":50,"type":"integer","minimum":1,"maximum":500}`       |

## upgrade_container_image

**Upgrade a Container's Image** · Risk: **write**

Pulls the newest image for an existing container and keeps its settings (`/container repull`). The container must be stopped; pass `stop=true` to stop it first. What survives: everything in the container's MOUNTS, its env list and its settings. What is LOST: files the container wrote inside its own root directory, because the image is unpacked again. So a container with no mount is refused unless you pass `accept_data_loss=true`. DEFAULTS TO A DRY RUN (`apply=false`) that shows the image, the mounts that protect data, and the steps. The pull runs in the background: check `get_container` until the status is `stopped`, then `start_container`. On a RouterOS version without `repull`, the tool says so and changes nothing.

| Parameter          | Required | Definition                                                                              |
| ------------------ | -------- | --------------------------------------------------------------------------------------- |
| `name`             | Yes      | Container name `{"type":"string","pattern":"^[A-Za-z0-9][A-Za-z0-9_.-]{0,40}$"}`        |
| `stop`             | Yes      | Stop the container first when it runs `{"default":false,"type":"boolean"}`              |
| `accept_data_loss` | Yes      | Allow the upgrade of a container that has no mount `{"default":false,"type":"boolean"}` |
| `apply`            | Yes      | false = show the plan; true = upgrade `{"default":false,"type":"boolean"}`              |

## deploy_container_stack

**Deploy Containers From One Description** · Risk: **write**

Creates one or more containers from a single description, as a compose file does. For each service it creates the veth interface (and adds it to a bridge when you name one), an env list, the mounts, and the container itself with the image, in the right order. DEFAULTS TO A DRY RUN (`apply=false`) that returns every command, with env values hidden. Before it writes anything, every command is parsed on the router; if one is not valid for that RouterOS version, nothing is written. It picks the setting names the router knows (`envlists`/`mountlists`, or the older `envlist`/`mounts`). A service whose container name already exists is skipped, so the tool can be run again after a failure. It does NOT start the containers: the image is pulled in the background, so wait until `get_container` shows `stopped`, then `start_container`. The router must have the container package and container mode enabled (`get_routeros_container_guide`). It does not add firewall or NAT rules for the containers.
